# v2 架构与边界

## 模块职责

| 模块 | 职责 |
| --- | --- |
| `types.py` / `config.py` | 不可变数据契约、可校验配置 |
| `data.py` | 显式读取、规范化、稳定 ID、分组切分与指纹 |
| `chunking.py` | 答案正文分块，保留问题、来源、字符偏移 |
| `retrieval.py` | 离线 cosine 基线、固定模型版本的 Chroma 索引 |
| `rerank.py` | 缓存 CrossEncoder，对候选重排 |
| `pipeline.py` | 请求校验、并发限制、逐条筛选、证据预算、引用检查 |
| `prompts.py` / `generation.py` | 共用消息格式、摘录或 Transformers 生成 |
| `factory.py` | 统一依赖装配，模型实例在服务生命周期内复用 |
| `cli.py` / `api.py` / `ui.py` | 输入输出适配，不重复业务逻辑 |
| `evaluation.py` / `training.py` | 明确评测口径、一次切分、仅答案监督 |

## 请求契约

`Answer` 包含 `status`、`text`、`evidence`、`citations`、`trace_id`、`timings_ms`、`reason`。

- `answered`：通过来源编号检查，不表示医学事实被验证。
- `insufficient_evidence`：无足够片段，或生成结果缺少合法引用。
- `error`：后端不可用或服务忙；API 返回 503，不返回无依据的替代答案。

`evidence` 是实际送给生成器的片段；`citations` 是输出中实际出现的编号。二者不能解释为“每条陈述都已得到支持”。没有做逐句蕴含验证或临床正确性判断。

## 存储和重建

`data/train.json` 等旧数据保持不变。v2 数据 ID 与内容有关，不依赖读取顺序；来源字段单独保存。相同正文的不同问题仍然保有不同 ID。完全相同记录重复出现时，保留第一次出现的来源。

新索引写入新的目录，包含 `chunks.json`、`manifest.json`，以及可选 `chroma/`。manifest 记录语料/片段哈希、分块参数、模型 commit、维度和 cosine 距离空间。读取时检查片段指纹与数量，Chroma 还检查条数和距离空间。

离线索引先写临时目录再重命名。Chroma 的 SQLite 连接在 Windows 可能持有文件句柄，因此在新目标目录构建，最后写 manifest 作为完成标记。失败的目录不能被读取；如果进程崩溃或 Windows 文件占用导致临时内容无法清理，应确认服务停止后删除未完成目录，或换一个新目录重建。不原地更改正在服务的索引，不承诺断点续建。

## 明确限制

1. 默认阈值未校准，词汇重合不能证明问题与答案的关系正确。
2. 答案块保证有正文，不能保证每块包含原记录的全部条件。长答案可能仍跨块拆分；困难样本应评估父文档扩展或相邻块恢复的收益。
3. 字符预算与模型 token 预算不同；后者在 tokenizer 后验证，超限报错。
4. 提示词把资料视为不可信输入，但这不是提示注入攻击的完备防御。
5. 共享锁提供单进程背压，不是高并发推理调度器。多 worker 会各加载一份模型。
6. `health` 只表示服务进程已建立；生成模型延迟加载，不能把它当作模型热就绪检查。
7. CLI eval 的原始检索指标在门控前计算；最终证据及拒答需看端到端记录。
8. 医疗语料仍需质量审查、许可核查和适用人群/时效元数据；本次重构没有替语料增加临床权威性。
